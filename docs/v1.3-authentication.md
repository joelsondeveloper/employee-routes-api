# V1.3: PostgreSQL e autenticação Google

## Ambiente

O backend usa PostgreSQL quando `DATABASE_URL` está configurada. O SQLite continua disponível para desenvolvimento/testes locais e não é usado pelo runtime de produção com PostgreSQL.

Variáveis do backend:

- `DATABASE_URL`: URL privada do PostgreSQL Railway.
- `GOOGLE_CLIENT_ID`: client ID web público usado para validar tokens do Google.
- `LOCATIONIQ_API_KEY`: segredo somente do backend.
- `FRONTEND_ORIGIN`: origem exata do frontend.
- `NODE_ENV=production` e `PORT`.

O frontend usa somente `VITE_API_URL` e `VITE_GOOGLE_CLIENT_ID`. Client IDs do Google são públicos; chaves secretas nunca devem ser colocadas em variáveis `VITE_*`.

## Fluxo de login

1. O botão oficial do Google Identity Services no frontend recebe um ID token.
2. O frontend envia `POST /api/auth/google` com `{ "credential": "..." }`.
3. O Express valida assinatura, emissor, audiência e expiração com `google-auth-library`.
4. O primeiro login cria `users`, `organizations` e uma `memberships` `ADMIN`.
5. O backend grava o ID token em cookie `HttpOnly`; o navegador envia o cookie automaticamente nas chamadas privadas. O Bearer continua aceito como fallback para clientes técnicos.

## Isolamento

Funcionários carregados pelo backend sempre são filtrados pelo `organization_id` resolvido a partir do token validado. IDs fornecidos pelo navegador não determinam a organização.

Rotas privadas: `/employees`, `/api/geocoding/preview`, `/api/routes/optimize` e `/api/routes/recalculate`.

Rotas públicas: `/health`, `/` e `POST /api/auth/google`.

Sem token, a API retorna `401`. Falhas de configuração retornam erro sanitizado e são registradas somente por nome/status no servidor.
